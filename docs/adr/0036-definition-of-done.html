Definition of Done: vier Ebenen Accepted

#Context

The roadmap (see docs/roadmap-1.0.html) sets a professional-engineering bar, but a bar without a definition of done is not checkable: "Phase fertig" and "1.0 fertig" would remain feelings. The grilling session therefore fixed a Definition of Done on four levels (stakeholder decision D13: four, explicitly including a per-REQ level). The per-REQ level is the semantic definition of the register's Done status — not a second bookkeeping.

#Decision

DoD 1 — Ticket/Slice. A slice is done when:

  • TDD red→green; typecheck + oxlint green; review gate passed (draft PR → Musti).
  • Acceptance test exists on the tier the REQ demands (PR #249 ruling).
  • No bespoke machinery: framework/library standard first; any deviation needs an ADR.
  • Comments explain why, never what; touched files trimmed.
  • A security/performance posture line is present in the PR: does the slice touch these axes? If yes, the guarding test or measurement is linked (or a deliberately documented non-requirement with reason); if no, a one-sentence "n/a" with reason. The reviewer checks this line like every other gate line (D16 — a checkable statement, not a rubber stamp).
  • ADR followed up where an architectural decision was made; register maintained where a REQ is touched.

DoD 2 — REQ (register Done). A REQ is Done when: acceptance test on the demanded tier · green on main in CI · register row cites the test location · review passed · ADR where required. No per-REQ demo/sign-off — that is the 1.0 level's job (D14).

DoD 3 — Phase. All tickets meet DoD 1; all blocking edges resolved; the phase is demoable on the real environment (from phase 1; the foundation itself: green gates + local production-shaped stack, because the real environment is the parallel infra track); roadmap status column and progress.db context updated to done (D17). No per-phase stakeholder sign-off.

DoD 4 — 1.0 (product, "zeigbar").

  1. ADR-001–042 scope implemented — or individual items consciously gated (only by NexusHero decision, visible in the register).
  2. One complete stakeholder walk-through without manual intervention — guest → registration → interview → computation → submission-ready → export — on the real URL, run by NexusHero and at least one external tester, recorded as evidence (D18).
  3. Deployed on k3s/Hetzner with backups/DR; REQ-010 closed; mantle REQs 007/008/009 green.
  4. DSGVO final audit before the first real account.
  5. Pre-go-live load test passed.
  6. No "AI smell": the phase 0.2 bespoke list replaced, comment discipline repo-wide.
  7. ELSTER submission activated once the manufacturer certificate arrives (external track). Amended by ADR-0050 (2026-10-28): 1.0 files on paper — form printout per BMF letter of 12.08.2022, paid unlock per tax year, legal pages reviewed by a lawyer. ELSTER becomes a 1.x extension.

Enforcement (D19): the ticket DoD is a checkable checklist in the PR template; the reviewer confirms each line. Automatable parts run in CI already; "why-only" comments and "no bespoke machinery" are review judgements and are not simulated with lint rules. The four levels live in docs/process/ and are wired into the PR template in phase 0.1.

Exceptions (D20): Musti may approve a DoD deviation; it is recorded visibly in the PR and the register with reason and a follow-up ticket; NexusHero keeps veto. The 1.0 core criteria (2 and 3) admit no exceptions — only a go-live deferral.

#Consequences

  • Four levels carry administration; the REQ level is anchored to the register's existing status semantics (Musti's PR #249 ruling), not a parallel track.
  • The posture line forces a conscious security/performance answer on every ticket without mandating tests where no axis is touched (no test proliferation).
  • The recorded stakeholder walk-through makes "zeigbar" provable (ADR-0021 spirit: observed, not claimed).
  • Deviations stay visible: the mechanism the project already lives (REQ-010 A1, the #175 footer note) becomes the rule instead of an ad-hoc practice.
