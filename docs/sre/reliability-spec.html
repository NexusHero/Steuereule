Architecture as of 2026-11-28

Reliability

Reliability: targets, protection and gaps

  • 1. Targets
  • 2. Alerts that exist
  • 3. What protects the service
  • 4. What is missing

What the service is meant to deliver, what protects it today, and what is missing. Everything in sections 2 and 3 exists in the repository and names its file. What does not exist is in section 4 and in §11 of the architecture; it is not described here as if it did.

As of 2026-11-28. Checked against infra/gcp/, .github/workflows/deploy.yml and apps/api/src.

#1. Targets

These are targets. None of them is measured today: no indicator is computed from the request metrics, and no alert is tied to a target (section 4).

What Target Window
API availability: answers without a 5xx, of all requests that are not a client error 99.9 % 30 days, rolling
Cockpit read, GET /v1/steuerjahre/:jahr/cockpit, whole round trip p95 ≤ 120 ms, p99 ≤ 250 ms 30 days, rolling
Printed return, from the request to the finished PDF p95 ≤ 3.5 s, p99 ≤ 6 s 30 days, rolling

99.9 % allows about 43 minutes a month. Two properties of the deployment work against it and are accepted for the beta: the services scale to zero, so the first request after a pause waits for a cold start, and beta and staging run the database in one zone on a shared-core tier that the Cloud SQL SLA does not cover. Production runs the database regionally with a standby by default (db_high_availability in infra/gcp/main.tf).

Intended policy once the targets are measured: when half of a month's allowance is used, reliability work comes before new features; when all of it is used, only fixes are deployed until the cause is written up.

#2. Alerts that exist

Six alert policies in Google Cloud Monitoring, defined in infra/gcp/monitoring.tf. They exist only when the variable alert_email is set; the uptime check also needs api_hostname. They send an e-mail. There is no paging tool and no on-call rotation. What each alert means and what to check first is in the incident runbook.

Alert Fires when
API down the uptime check on /v1/health/live fails from every location for 3 minutes
5xx share more than 5 % of the API's requests end in a 5xx over 5 minutes
Container crash a Cloud Run log line reports a memory limit, a termination signal or an exit
Unhandled errors three or more unexpected errors within 5 minutes
Cloud SQL disk disk utilisation above 80 % for 5 minutes
Cloud SQL CPU CPU utilisation above 80 % over 15 minutes

#3. What protects the service

Mechanism What it does Where
Health probes /v1/health/live answers without touching the database, so a database blip does not restart the container; /v1/health/ready checks that the database is reachable apps/api/src/health/
Shutdown on SIGTERM the API stops accepting and lets requests in flight finish; after an unhandled rejection it drains for at most 10 seconds and exits enableShutdownHooks in main.ts, llm/provider-rejections.ts, ADR-0109
Database pool each instance opens at most (vCPUs × 2) + 1 connections, at least 3, unless DATABASE_URL sets its own limit. On the 1 vCPU of the API that is 3 per instance, 30 on ten instances config/runtime-capacity.ts
Limits on costly work at most 4 uploads in flight per instance and 1 per account; the PDF renderer of the account export holds at most 8 waiting renders and a render times out after 60 seconds; an account holds at most 3 print jobs; model calls have a daily cap across all users. A refused request gets 429 with Retry-After ADR-0109
Rate limits across instances every limit counts in one shared storage, Redis by default rate-limit/shared-throttler-storage.ts
Backups the application database: a backup every night, point-in-time recovery with 7 days of logs, 7 backups kept. The keystore: 2 backups and 1 day of logs on purpose, so a deleted key does not live on in a backup (ADR-0059) infra/gcp/main.tf
Rollout the deploy takes a backup, starts a new revision and routes traffic back to the previous one when it fails .github/workflows/deploy.yml

With point-in-time recovery the data that can be lost is what was written since the last log the database shipped. How long a recovery takes has not been measured (section 4).

#4. What is missing

Gap Consequence
No indicator is measured. The targets of section 1 are not computed anywhere nobody knows whether a target is met
No burn-rate alert. The 5xx alert fires at 5 %, fifty times the allowance of the availability target a slow loss of the month's allowance goes unnoticed
No recovery exercise has been run. Restoring the database from a backup and bringing the services up in a fresh project has never been done the time to recover is unknown; a recovery time must not be promised
No paging and no on-call. Alerts are e-mails an outage at night is seen in the morning
Readiness does not look at load. /v1/health/ready checks the database only; a busy event loop does not take an instance out of rotation an overloaded instance keeps receiving requests
Traces are collected nowhere (architecture §8.5) a slow request cannot be followed across its steps
Print jobs live in process memory (architecture §11, finding 1) a restart loses a running job
No load figures. Expected users, the peak before the filing deadline and the cost of an answer of the owl are not written down capacity is set by defaults, not by a model
