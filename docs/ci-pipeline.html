What every CI gate is, which category it belongs to, what it proves, and whether it blocks a merge. The single overview of "what the pipeline actually does". The taxonomy and the per-PR CI-Overview comment that mirrors this map are decided in ADR-0105.

Checks are named category: gate so the GitHub PR checklist clusters by category on its own. The five PR pipelines (Quality, Build & E2E, Security, Load, and the advisory CI Overview) run in parallel on every pull request; the nightly ones (AI eval, Law watch) do not gate PRs.

#Required checks (ruleset main)

A repository ruleset (main, active, no bypass actors) requires status checks by name. A classic branch protection for main exists beside it (no force push, no deletion, conversation resolution, applies to admins); it lists no status checks, the ruleset does. The names below are the job name: values exactly as they report. On 2026-11-24 the ruleset required the first twenty (read with gh api); the last five are not required yet and must be added by a repository admin (H2-32). Each of them runs on every pull request, so requiring it cannot leave a PR waiting.

Since 2026-11-26 the ruleset also requires the branch to be up to date with main before merging: when main moves, an open pull request is updated and its checks run again against the new base. A merge queue is not available to a repository owned by a user account.

#Release (production deploy, ADR-0113)

release.yml ("Release") runs when a GitHub Release is published for a tag vX.Y.Z, or by hand from a tag to deploy a release again. Job release: guard (tag on main, CI green) refuses unless the ref is a vMAJOR.MINOR.PATCH tag, its commit is on main and "Build & E2E" passed on exactly that commit as a push run (scripts/release/guard.sh, decision in scripts/release/guard.mjs, tested by guard.test.mjs in the job static: docs consistency (register + adr)). Job release: deploy to production then calls deploy.yml for the GitHub environment production: its reviewers approve, and the API image that staging ran for that commit (api:staging-ok-<commit>) is copied into the production registry with the same digest, not rebuilt. The web and website images are still built per environment. deploy.yml itself runs only for staging (after a green "Build & E2E" on main, or by hand) and for the Release workflow; it has no pull_request trigger, so a pull request shows no skipped deploy jobs.

#How the browser gates are split (ADR-0112)

The 46 stack-bound E2E gates are listed in e2e/gates.json, each in one group. Build & E2E builds the API and the web bundle once (e2e: build), then runs one job per group in parallel, each on a fresh stack (e2e: gates — <group>). A group reports every failing gate, not only the first.

Group What it holds
layout Responsive layout, banners, dark mode, visual regression
a11y BFSG / WCAG 2.1 AA, both themes, keyboard
chat-and-inputs Owl chat experience, input aids, smart inputs, dictation, plan in chat
account-and-session Cross-origin sign-up, session, device QR, account security
tax-flows Household, church tax, real cases, forms, printout, Verlauf, S10 acceptance
navigation-and-states Deep links, hub, sheets, deadline banners and failure states, Belege channel
beta-states Beta account, partner, payment and mask states
scan-and-uploads Self-hosted OCR, scan corpus and flows, uploads
budgets Navigation efficiency, load and latency budget
static-ratchet E2E coverage ratchet and the gate-list check (no stack)
owl-fake-ki Owl mode against the scripted chat model (AI_FAKE_KI)

Adding a gate is one entry in e2e/gates.json; the matrix is built from the file, so a gate cannot exist without running. node e2e/run-gates.mjs --list shows the gates, --group <g> runs one group against a stack that is already up.

The two required checks that were one job each keep their names as aggregate jobs that wait for the parts and run if: always(), so a ruleset that pins the name never waits for a job that no longer exists:

  • e2e: browser gates & a11y (BFSG/WCAG 2.1 AA, headless Chromium) = plan + build + every e2e: gates — <group>
  • e2e: production compose stack + OWASP ZAP DAST (real Docker build) = e2e: production stack smoke + e2e: OWASP ZAP DAST (real Docker build)

The set-up shared by the jobs is in .github/actions/ (setup-workspace, prepare-database, install-chromium, boot-prod-stack); long shell steps live in e2e/smoke/, e2e/prod-deploy/, scripts/ci/ and scripts/deploy/ (the two deploy steps that run before the checkout stay inline).

#Control proofs: a gate must fail on its mutant

e2e/control-proofs.json lists planted regressions, each with the gate that must catch it and the message that gate must fail with (ADR-0021). Every entry runs on every pull request as one more job of the gate matrix (e2e: gates — control-proof-<id>): the job applies the mutation to the API source, rebuilds the API, boots the stack and runs the gate. It passes only when the gate fails with the expected message. If the gate passes on the mutant, or is red for another reason, the job fails. A mutation is a literal find/replace that must match its file exactly once; when a refactoring moves the line, e2e: plan fails and names the proof. To add one: an entry in control-proofs.json, nothing in the workflow.

Proof Mutant Gate that must fail
fresh-age-default session.freshAge: 0 removed (ADR-0027) e2e/device/device-authorization.mjs

#The accessibility and DAST caveat

The a11y (BFSG/WCAG) gates are the a11y group of the browser gates and no longer share a stack with unrelated gates. The OWASP ZAP DAST pentest is its own job on the real production containers; the Docker stack is built twice (smoke and DAST) on purpose (ADR-0112, replacing the choice of ADR-0105).
