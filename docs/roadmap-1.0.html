#Goal

Steuereule becomes a real product that competes with Taxfix, WISO Steuer, wundertax and Steuerbot (D1). The functional goal is the complete 1.0 vision from the product ADRs 001–042: employees in 5 life situations, Grenzgänger-CH (cross-border commuters to Switzerland), pensioners, capital, rental income (simple), document inbox, Günstigerprüfung (most-favorable-treatment check), Bescheid check (Bescheid: tax assessment notice), deadline warning mode, owl AI — not a single slice, but a staged roadmap (D2).

The quality bar (D3): professional engineering instead of AI bloat.

  1. No custom build where the framework is the answer — NestJS standard and established libraries first; every deviation needs an ADR.
  2. Slices are one product, not a collection — one navigation, one session/data flow, one shared domain core.
  3. Comments explain why, never what — file-header comments are trimmed when touched.
  4. Measurable enforcement through the Definition of Done (see below).

#Definition of Done — four levels (D13–D20)

Introduced by ADR-0036 (engineering). Enforcement: PR checklist + review tick; exceptions visible + approved + justified + with a catch-up ticket.

#1. DoD ticket/slice

  • TDD red→green; typecheck + oxlint green; review gate passed (draft PR → Musti).
  • Acceptance test at the tier the REQ requires (Musti ruling PR #249).
  • No custom build without an ADR; framework/library standard first.
  • Comments why-only; touched files trimmed.
  • Security/performance posture line in the PR: axis touched? Test/measurement linked — or a justified "n/a". The reviewer ticks off the line (D16).
  • ADR added for an architecture decision; register maintained when a REQ is touched.

#2. DoD REQ (register status "Done")

  • Acceptance test exists at the required tier · green on main in CI · register line cites the test location · review passed · ADR where needed (D14).
  • No demo/sign-off per REQ — the 1.0 level does that.

#3. DoD phase

  • All tickets meet the ticket DoD; all blocking edges resolved.
  • The phase is demoable on the real environment (from phase 1; foundation: gates green + local prod-shape stack, because the real environment is the parallel infra track).
  • Roadmap status column updated; progress.db context set to erledigt (D17).

#4. DoD 1.0 (product, "showable")

  1. ADR-001–042 scope implemented — or individual items deliberately "gated" (only by NexusHero decision, visible in the register).
  2. One complete stakeholder run-through without manual intervention — guest → registration → interview → calculation → ready to file → export — on the real URL. Performed by NexusHero and at least one external test user, recorded as evidence (D18).
  3. Deployed on k3s/Hetzner with backups/DR; REQ-010 closed; shell REQs 007/008/009 green.
  4. Final DSGVO audit before the first real account.
  5. Pre-go-live load test passed.
  6. No "AI smell": custom-build list from phase 0.2 replaced, comment discipline repo-wide.
  7. ELSTER transmission activated → paper route (ADR-0050): form printout per BMF letter of 12.08.2022, unlock paid per tax year, legal pages reviewed by a lawyer. ELSTER follows as 1.x.

Exceptions (D20): Musti approves DoD deviations; visible in the PR and the register with a reason and a catch-up ticket; NexusHero keeps a veto. There are no exceptions to the 1.0 core criteria (2 and 3) — there, only a go-live postponement.

#Process (unchanged, D11)

Every phase runs through the existing crew flow: to-spec → to-tickets (tracer slices with blocking edges; the phase tickets here are cut finely at phase start) → implement (TDD) → code-review. Decisions D1–D21 are recorded as ADRs (ADR-0035/0036 in docs/adr/, ADR-051 in the research log), including amendments where existing ADRs are touched (ADR-0015 lesson for D5, ADR-0026 (#292 gap, closed by the infra track), product ADR-027(b) for REQ-007 — supersession on the 2FA point, enforcement in ticket 05). The register gets new REQs for the product features as soon as the phases cut them.

#Time frame (D12)

No calendar dates. Relative phases with effort in crew slices; the only external pacemaker is the ELSTER application (running from now on). If a target date emerges, the plan is readjusted backwards from the date — explicitly as a decision, not gradually.

#Agent staffing (D21)

4 pro roles at once — more is not faster because of the blocking graph:

Role (crew persona) Task
Author track A (full-stack) P0 chain (sequential) → P1 employees → P2/P3 shares
Author track B (full-stack) from P1: Grenzgänger-CH in parallel
Reviewer (Musti) dedicated, never authors — every draft PR re-read in a fresh context (ADR-0022)
Infra/DevOps (Salih) Track 06 (#292) from start to finish

NexusHero orchestrates and handles the ELSTER application (external, not an agent job).

Rationale: P0 is a strict chain (one active code thread; only infra in parallel) · P1 is the peak with 2 verticals + infra + reviewer = 4 · review remains the bottleneck (ADR-0015: N authors, 1 reviewer ⇒ backlog with more authors) · three authors on the shared core = merge conflicts · no coordination seat (ADR-0016: tickets and ADRs are the coordination).

Scaling exception: In P2, 3 authors may run temporarily if pensioners/capital/rental income are cut as real parallel sub-tracks — only as long as the review queue stays empty (formula: authors ≤ review throughput − 1). All roles run on Pro; the reviewer needs at least author quality, because he is the bottleneck.

#Risks (honest)

  • The foundation is large (D9) → the internal order 0.1 → 0.5 is mandatory, the WIP limit applies.
  • Parallel verticals (D5) → divergence risk at the core; countermeasure: shared core review gate; review capacity is the bottleneck (ADR-0015).
  • ELSTER certificate → external timeline; since ADR-0050 no longer on the 1.0 path.
  • Vordruck templates (ADR-0050) → to be obtained and updated per tax year; whether a filled-in portal PDF counts as an official Vordruck must be clarified before the first sale.
  • The 1.0 scope is very large → if capacity breaks, pensioners/capital/rental income stay honestly "gated" — the decision stays with NexusHero, visible in the register.
  • DoD proliferation → four levels carry administration; the REQ level is the semantic definition of the register status and not a second set of books (D13).
